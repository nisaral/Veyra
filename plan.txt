# Status: rejected superset

The runnable project is `veyra/`. Its source of truth is `veyra/docs/ARCHITECTURE.md`
and `veyra/docs/PREREGISTRATION.md`. This file is the larger execution-OS sketch
that v0.1 deliberately did not build: control plane, marketplace, ClickHouse,
Kubernetes, a Jev-model zoo, and a second public SDK. Do not implement those
from this document.

# Adaptive Agent Execution Runtime

## Working concept

Build an open-source, model-agnostic runtime for long-horizon AI agents.

The runtime does not require users to replace their preferred agent framework.

Instead, it sits one level above or around existing agent systems and dynamically decides:

- which model should execute the next step,
- whether a model call is even necessary,
- which tool should be used,
- whether a specialist agent should be invoked,
- whether to use one agent or multiple agents,
- how much context/memory should be supplied,
- whether to verify,
- whether to retry,
- whether to parallelize,
- whether to ask for human approval,
- and when to terminate.

The core abstraction is:

    TASK STATE
        ↓
    DECISION
        ↓
    ACTION
        ↓
    OBSERVATION
        ↓
    UPDATED STATE
        ↓
    DECISION
        ↓
       ...

The runtime is therefore an **adaptive execution scheduler for intelligence**.

---

# 1. Why this is worth building

The agent-framework market is already crowded.

OpenAI Agents SDK provides agents, tools, handoffs, guardrails, sandbox agents and tracing.

Google ADK 2.0 already provides graph workflows, routing, loops, retries, fan-out/fan-in, dynamic nodes, state and human-in-the-loop workflows.

Microsoft Agent Framework similarly provides agents, middleware, workflows, routing, checkpointing, observability, MCP and A2A integrations, including a Go implementation.

OpenHands already provides a serious coding-agent runtime with tools, workspaces and agent execution infrastructure.

MCP is now a major interoperability layer, with its Python SDK v2 supporting the July 28, 2026 specification and standard transports.

A2A provides a standard way for remote agents to discover capabilities and collaborate without exposing their internal state/tools.

Most importantly, HarnessX already explicitly combines harness composition, model routing, plugins, benchmark adapters, RL trajectories, harness evolution and a community hub.

Therefore:

DO NOT build:

    "another agent framework"

DO NOT build:

    "LangGraph but smaller"

DO NOT build:

    "another plugin-based agent SDK"

DO NOT build:

    "another LLM router"

Instead build:

    "an adaptive runtime that schedules computation across
     models, tools, agents and harnesses according to live task state."

That is the core differentiation.

---

# 2. Core research thesis

The research thesis should be:

> Agent execution should be treated as a sequential decision problem rather than a fixed workflow.

A conventional agent:

    prompt
      ↓
    model
      ↓
    tool
      ↓
    model
      ↓
    tool
      ↓
    answer

Our runtime:

    prompt
      ↓
    state estimator
      ↓
    decision model
      ↓
    policy
      ↓
    best action
      ↓
    observation
      ↓
    state update
      ↓
    decision model
      ↓
    best action
      ↓
    ...

The optimal action can change after every observation.

---

# 3. The key innovation

The runtime should route **execution**, not just models.

The candidate action space should include:

    MODEL_CALL
    TOOL_CALL
    RETRIEVAL
    MEMORY_LOOKUP
    MEMORY_COMPACTION
    SPECIALIST_AGENT
    DIFFERENT_HARNESS
    PARALLEL_BRANCH
    VERIFY
    RETRY
    HUMAN_APPROVAL
    TERMINATE

This creates a much richer routing problem.

Example:

    "Migrate Flask application to FastAPI"

Step 1:
    cheap local model → inspect repository

Step 2:
    deterministic AST/dependency analysis

Step 3:
    decision model

    migration_complexity = 0.87

Step 4:
    coding agent

Step 5:
    tests

Step 6:
    decision model

    failure_probability = 0.72

Step 7:
    debugger specialist

Step 8:
    retrieve framework migration knowledge

Step 9:
    coding agent

Step 10:
    verification

Step 11:
    deployment/canary agent

Another task:

    "Add a health endpoint"

could become:

    cheap model
      ↓
    edit
      ↓
    test
      ↓
    done

Same runtime.

Different execution strategy.

# 4. This should become the defining product primitive

Define:

    ActionCandidate

with fields roughly equivalent to:

    action_id
    type
    provider
    capability
    estimated_cost
    estimated_latency
    expected_success
    risk
    required_permissions
    required_context
    input_schema
    output_schema

The decision engine evaluates a set of candidates.

For example:

    candidates:

      1. local_4b
      2. local_14b
      3. coding_agent
      4. browser_agent
      5. static_analyzer
      6. verifier
      7. human

Then the policy chooses.

This is the central object of the whole runtime.

# 5. Jev-style models become decision backends

Do not make Jev mandatory.

Create:

    DecisionModel

interface.

Possible implementations:

    Heuristic
    SemIf
    Von
    Laya
    Kev
    Nimble
    NanoJev
    RouteLLM
    DIO-DM
    Jev adapter

The current open-source ecosystem now contains several Jev-inspired approaches, including Von, Kev, Laya, Nimble, SemIf and NanoJev. Their architectures differ substantially, which makes them useful as an experimental family rather than a dependency you have to pick in advance.

The DataCamp survey also emphasizes that these projects differ in their architecture, parameter count and approach to typed decisions, while noting that the ecosystem is extremely young. Therefore the runtime should abstract over them rather than assume one is universally superior. 

The decision interface should be:

    state
      +
    question/schema
      ↓
    probabilities

For example:

    should_use_coding_agent?
        YES: 0.82
        NO:  0.18

    should_verify?
        YES: 0.91
        NO:  0.09

    candidate_harness:
        OpenHands: 0.62
        custom:    0.23
        LangGraph: 0.15

The runtime then applies deterministic policy constraints.

# 6. Extremely important separation

Never let the decision model directly execute actions.

Correct:

    Decision model
        ↓
    Policy engine
        ↓
    Capability/security check
        ↓
    Scheduler
        ↓
    Executor

Incorrect:

    LLM
      ↓
    kubectl / shell / browser / deployment

The decision model predicts.

The policy decides.

The executor acts.

The verifier validates.

This separation is central to making the system trustworthy.

# 7. The novel features to pursue

These are the areas that can differentiate the project from HarnessX and other runtimes.

## A. Step-level adaptive routing

Most routing asks:

    Which model should answer this?

Your runtime asks:

    What action should happen next?

This is the main contribution.

---

## B. Harness switching

An agent can change execution environment mid-task.

Example:

    custom lightweight harness
          ↓
    task gets difficult
          ↓
    switch to OpenHands
          ↓
    coding problem solved
          ↓
    return to lightweight harness
          ↓
    verifier

This is much more interesting than model switching.

Existing frameworks generally let you choose/compose the harness up front. Your runtime can make that choice dynamically.

---

## C. Verifier routing

Do not always use the same verifier.

The runtime chooses:

    deterministic test
    static analysis
    unit test
    schema validator
    small judge
    large judge
    second model
    human

depending on risk.

Example:

    trivial JSON transformation
        → schema validator

    financial calculation
        → deterministic calculator + verifier

    code migration
        → test suite + independent agent

This turns verification into another decision problem.

---

## D. Failure-directed escalation

When something fails, don't blindly retry.

Classify the failure:

    tool failure
    environment failure
    reasoning failure
    context failure
    model failure
    permission failure
    ambiguous task

Then route accordingly.

Example:

    test failure
       ↓
    decision model
       ↓
    likely context failure = 0.82
       ↓
    retrieve missing dependency documentation
       ↓
    retry

versus:

    test failure
       ↓
    likely code reasoning failure = 0.79
       ↓
    coding specialist
       ↓
    retry

This is a strong differentiator.

---

# 8. Compute economics

Every action should have an estimated cost.

For model:

    token cost

For tool:

    API cost

For browser:

    browser time

For agent:

    model + tool cost

For human:

    expensive

For infrastructure:

    GPU time

Now the runtime can optimize:

    probability_of_success
    ----------------------
    expected_cost + latency_penalty

This gives the runtime a common economic language across heterogeneous actions.

---

# 9. Execution budget

Every task receives:

    token_budget
    dollar_budget
    time_budget
    action_budget
    tool_budget
    risk_budget

Example:

    Task budget:

        $0.50
        4 minutes
        30 actions

The runtime may choose:

    cheap model

until confidence drops.

Then spend:

    $0.15

on a stronger specialist.

Then verify.

This creates a very clean research concept:

> Adaptive intelligence under a computation budget.

# 10. RL formulation

Use RL lightly but meaningfully.

The runtime is naturally a sequential decision process.

State:

    current task state
    previous actions
    observations
    confidence
    remaining budget
    model availability
    tool availability
    historical success
    context size
    elapsed time

Action:

    model
    tool
    subagent
    harness
    verifier
    retry
    parallelize
    terminate

Reward:

    successful task
      - cost
      - latency
      - unnecessary actions
      - failure penalties

For example:

    R =
        success
        - λ(cost)
        - μ(latency)
        - η(failed_actions)

The first algorithms should be:

    heuristic
    LinUCB
    contextual Thompson Sampling

Do NOT start with PPO.

# 11. A very interesting RL extension

Use the agent trajectory as a source of training data.

Example:

    state S1
      ↓
    action A1
      ↓
    observation O1
      ↓
    state S2
      ↓
    action A2
      ↓
    success

Store:

    (S1, A1, reward)
    (S2, A2, reward)

Then train the policy offline.

Eventually:

    production trajectories
        ↓
    de-identification
        ↓
    trajectory dataset
        ↓
    offline policy evaluation
        ↓
    policy update
        ↓
    shadow
        ↓
    canary
        ↓
    online

This becomes the data flywheel.

# 12. Counterfactual replay

This is one of the features I would push especially hard.

Suppose the runtime did:

    S
     ↓
    A = coding agent
     ↓
    success

The system should ask:

    "What would have happened if we had used
     the smaller model?"

or:

    "What if we had run static analysis first?"

Store alternative outcomes where possible.

Use cached outputs and benchmark traces to estimate:

    action value

This gives you:

> counterfactual policy evaluation for agent execution.

That is much more interesting than merely logging traces.

Be careful about scientific claims here; actual causal/counterfactual inference requires assumptions and should not be overstated. The first implementation can be offline replay rather than claiming causal certainty.

# 15. Use standards instead of inventing protocols

This is extremely important for adoption.

Use:

    MCP
    A2A
    OpenAI-compatible API
    OpenTelemetry
    OCI
    gRPC
    HTTP/WebSocket

MCP is already the standard mechanism for exposing tools/resources/prompts across agent applications, and its Python SDK v2 supports the July 2026 specification.

A2A should be used for remote agents rather than inventing another agent-to-agent protocol. A2A explicitly supports discovery, streaming, asynchronous tasks and structured data exchange.

Therefore:

    MCP = tool/plugin interoperability

    A2A = remote-agent interoperability

    gRPC = internal runtime communication

    HTTP = public API

# 16. Plugin manifest

Every plugin should publish machine-readable metadata.

Example:

    apiVersion: runtime.ai/v1

    name: openhands-coder
    type: agent

    capabilities:
      - code_editing
      - terminal
      - testing

    economics:
      estimated_latency_ms: 3000
      estimated_cost_usd: 0.04

    requirements:
      - filesystem
      - shell

    risk:
      level: high

    permissions:
      write_workspace: true
      network: false

    interface:
      protocol: grpc

This information is available to the decision layer.

Now routing can consider not only:

    "Is this model capable?"

but:

    "Is this capability worth its cost/risk/latency?"

# 17. Plugin isolation

There should be three plugin execution modes.

### In-process

For trusted lightweight plugins.

### Worker process

For Python/third-party plugins.

### Sandbox

For untrusted code/tools.

For sandboxing, support:

    Docker
    gVisor where available
    WASM/WASI for suitable deterministic plugins

Do not attempt to implement a complete sandbox yourself.

# 24. State Machine

The core runtime should be explicit.

    CREATED
       ↓
    INITIALIZING
       ↓
    PLANNING
       ↓
    EXECUTING
       ↓
    OBSERVING
       ↓
    DECIDING
       ↓
    VERIFYING
       ↓
    SUCCEEDED

Alternative transitions:

    EXECUTING → WAITING
    EXECUTING → FAILED
    FAILED → RECOVERING
    RECOVERING → EXECUTING
    EXECUTING → HUMAN_APPROVAL
    HUMAN_APPROVAL → EXECUTING
    HUMAN_APPROVAL → TERMINATED

Long-running execution must be resumable.

Every state transition must be persisted.

# 48. Benchmark the HARNESSES, not just models

This is one of the strongest research angles.

Recent analysis of public benchmark results found large same-model/different-harness differences, with a median gap of roughly 16 percentage points across a collection of same-model harness pairs. Treat such third-party analyses as evidence that the question matters, not as universal measurements; the exact effect depends strongly on benchmark and environment.

Your experiment should control:

    same model
    same task
    same tools
    same environment

Change:

    harness/runtime only

Then measure:

    success
    cost
    latency
    tool calls
    failures
    recovery
    trajectory length

There are also current studies explicitly questioning when harness engineering produces measurable gains and emphasizing that benefits may depend on task horizon.

That uncertainty is actually useful: your benchmark should investigate it rather than assume the answer.

# 108. Final technical philosophy

The runtime should always make this distinction:

    MODEL
        = generates / reasons

    TOOL
        = acts on environment

    AGENT
        = performs a specialized execution loop

    HARNESS
        = defines execution behavior

    DECISION MODEL
        = estimates which action is appropriate

    POLICY
        = decides what is allowed/optimal

    SCHEDULER
        = determines when and where to execute

    VERIFIER
        = determines whether the result is acceptable

    RL
        = learns how execution decisions should improve

    RUNTIME
        = coordinates all of the above

That is the architecture.
